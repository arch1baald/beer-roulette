# Beer Roulette Plan

## Goal
Собрать одностраничный сайт на чистом `HTML`, `CSS` и `JavaScript` без фреймворков, где пользователь открывает "пивной кейс" и видит анимированную рулетку в стиле игровых кейсов: лента с карточками быстро прокручивается, постепенно замедляется и останавливается на выигранном предмете, после чего приз показывается крупно на отдельном экране поверх страницы.

## Product Principles
- Один экран, один главный сценарий, минимум отвлекающих элементов.
- Сайт должен хорошо ощущаться и на десктопе, и на мобиле.
- Важнее всего не количество функций, а качество ощущения от спина.
- Визуал должен поддерживать атмосферу азарта и "редкого дропа", но без перегруза.
- Базовая реализация должна быть простой в поддержке и удобной для последующих экспериментов с визуалом и таймингами.

## Current Direction
На текущем этапе зафиксированы такие решения для первой рабочей версии:

1. Зону под изображением делать почти однотонной и светлой, без выраженного серого виньетирования.
2. Карточки делать чуть уже и выше, чтобы вытянутые бутылки помещались естественнее.
3. Интерфейс страницы держать максимально чистым: заголовок, рулетка, одна главная кнопка и reveal.
4. Убирать служебные пояснения вроде текущего статуса, технических подсказок и лишних описательных блоков.

## MVP Scope
В первой версии сайт должен уметь только главное:

1. Показывать рулетку сразу при открытии страницы.
2. Давать пользователю одну понятную кнопку запуска спина.
3. Запускать анимацию прокрутки ленты.
4. Останавливаться на заранее выбранном призе.
5. Показывать выигрыш крупно в режиме reveal.
6. Позволять крутить заново.

Все остальное пока не входит в обязательный объем:
- авторизация;
- история выпадений;
- инвентарь;
- реальные вероятности с настройкой через UI;
- несколько кейсов;
- серверная логика;
- звук;
- счетчики, рейтинги и прочие игровые системы.

## User Flow
### 1. Initial
- Пользователь открывает сайт.
- Сразу видит рулетку, центральный маркер и кнопку действия.
- Ниже или рядом может быть короткий текст, задающий настроение.

### 2. Spin Start
- Пользователь нажимает кнопку `Крутить`.
- Кнопка блокируется на время анимации.
- Лента начинает движение с заметным ускорением или сразу с высокой скоростью.

### 3. Spin Progress
- В окне рулетки пролетают карточки с пивом.
- Пользователь видит разные редкости и чувствует шанс на редкий дроп.
- На финальном отрезке лента замедляется.

### 4. Result Reveal
- Победивший предмет оказывается точно под центральным маркером.
- Через короткую драматичную паузу появляется полноэкранный reveal.
- На reveal-экране показываются:
  - крупная картинка;
  - название;
  - редкость;
  - кнопка `Крутить снова`.

### 5. Replay
- После закрытия reveal или по нажатию на повтор пользователь возвращается к исходному состоянию.
- Можно сразу запускать новый спин.

## Core States
Для логики страницы удобно сразу зафиксировать 3 основных состояния:

- `idle`  
  Страница готова к запуску. Кнопка активна. Reveal скрыт.

- `spinning`  
  Идет анимация. Повторный запуск заблокирован.

- `revealed`  
  Анимация завершена, приз показан крупно.

Этого достаточно для первого этапа. Если позже понадобится больше контроля, можно добавить промежуточные состояния вроде `slowing` или `transitioning`.

## Page Structure
Базовая структура `index.html` может быть такой:

1. `header`  
   Название проекта без лишнего служебного текста.

2. `main hero section`  
   Главный блок с рулеткой, центральным маркером и кнопкой.

3. `roulette viewport`  
   Видимая область, через которую пользователь наблюдает движение ленты.

4. `roulette track`  
   Внутренняя длинная лента с карточками предметов.

5. `cta area`  
   Одна главная кнопка запуска.

6. `result overlay`  
   Полноэкранный слой с reveal-карточкой выигранного предмета.

## Card Format Strategy
Так как исходные изображения пива не унифицированы и часть из них:
- сильно вытянуты по вертикали;
- уже лежат внутри прямоугольного кадра;
- местами содержат остатки белого фона,

карточки в рулетке нужно проектировать не как квадратные, а как вертикальные, ближе к "портретному" формату.

Рекомендация для первой версии:
- делать карточку визуально высокой;
- внутри карточки размещать изображение через `object-fit: contain`, а не `cover`;
- оставлять внутренние отступы вокруг изображения, чтобы бутылки и банки не упирались в края;
- не пытаться заполнять карточку картинкой целиком ценой обрезки или искажения.

Практический вывод:
- лучше видеть меньше карточек одновременно, но читать их крупно;
- на мобильной ширине допустимо, что во viewport помещается примерно `1-1.5` крупной карточки или немного больше;
- на десктопе можно показывать больше, но приоритет все равно остается за читаемостью предмета.

Это направление лучше подходит под товарные фото бутылок, чем сетка из квадратных игровых тайлов.

Дополнительное решение для MVP:
- карточки стоит сделать чуть уже текущего базового варианта;
- при этом сохранить или даже немного увеличить вертикальное ощущение высоты;
- текстовую часть на карточке держать проще и компактнее, чтобы больше места отдать самому предмету.

## Data Model
Для первой версии хватит простого массива объектов в `script`:

- `id`
- `name`
- `image`
- `rarity`
- `themeColor` или `glowClass`

Пример смысловой структуры:

```js
const items = [
  {
    id: "lager-classic",
    name: "Classic Lager",
    image: "assets/lager.png",
    rarity: "common",
    themeColor: "#7a7f8f"
  }
];
```

На старте можно использовать небольшой набор, например 8-12 предметов, а затем расширять коллекцию.

## Roulette Animation Approach
Чтобы рулетка выглядела убедительно и оставалась простой технически, лучше сразу принять такую модель:

1. Победитель выбирается до запуска анимации.
2. На ленту заранее выкладывается длинная последовательность карточек.
3. Победный предмет вставляется в рассчитанную финальную позицию.
4. Лента двигается через `transform: translateX(...)`.
5. Замедление происходит через easing или через заранее рассчитанную временную кривую.

Почему так лучше:
- проще контролировать результат;
- проще добиться красивой остановки точно по центру;
- меньше риск визуальных дерганий;
- проще менять длительность и характер замедления.

## What Should Be Decided Early
Некоторые вещи лучше продумать заранее, даже если финальный визуал еще не утвержден.

### 1. Формат ассетов
Нужно рано решить, какими будут изображения:
- прозрачные PNG/WebP предметов;
- одинаковые карточки с унифицированной рамкой;
- банки, бутылки или стилизованные постеры.

Это важно, потому что от этого зависит:
- размер карточек;
- способ кадрирования;
- качество на мобиле;
- общая цельность визуала.

На основе текущих ассетов уже можно принять несколько практических решений:
- считать бутылки и банки основным типом контента;
- ориентироваться на высокие карточки, а не на квадрат;
- готовиться к тому, что часть фото будет с белым или светлым фоном;
- опираться на мягкую подложку внутри карточки, чтобы фон исходника не выглядел чужеродно.

Выбранное направление для первой реализации:
- светлая почти однотонная медиазона под изображением;
- без сильного серого градиента вокруг бутылки;
- без попытки "спрятать" белый фон исходника темной виньеткой.

### 2. Набор редкостей
Лучше заранее определить 3-4 редкости, например:
- `common`
- `rare`
- `epic`
- `legendary`

Это поможет сразу заложить:
- цветовую систему;
- стили рамок;
- силу свечения;
- визуальный вес финального reveal.

### 3. Длительность спина
Нужно заранее определить целевой диапазон, который будем потом тюнить, например:
- стартовая гипотеза: `3.5-5 секунд` на один спин.

Это даст опору при первой реализации и упростит дальнейшие эксперименты.

### 4. Поведение на мобиле
Нужно сразу считать мобильную версию отдельным приоритетом, а не "сжатым десктопом":
- крупнее активная кнопка;
- меньше лишнего декора;
- лучше читается центральный предмет;
- reveal должен помещаться без визуального шума.

Дополнительно для мобилы:
- высоту карточки стоит закладывать смелее, чем ширину;
- нельзя рассчитывать на плотный ряд из множества мелких карточек;
- лучше показать меньше элементов в окне рулетки, но дать пользователю хорошо различать саму бутылку.

### 5. Политика повторного спина
Нужно заранее решить:
- новый спин только после закрытия reveal;
- или можно сразу крутить из reveal-кнопки.

Для MVP логичнее второй вариант: одна кнопка на reveal сразу запускает следующий цикл.

## UX Notes
- Пользователь должен понимать, где именно определяется результат: для этого нужен явный центральный маркер.
- Кнопка действия должна быть одна и максимально очевидная.
- Во время спина нельзя давать неоднозначных действий.
- Reveal должен ощущаться как награда, а не как просто еще один блок.
- Анимация не должна быть слишком длинной: интрига важна, но утомление сильнее убивает опыт.
- Если ассеты вытянуты вверх, интерфейс должен подстраиваться под них, а не наоборот.
- Небольшой остаточный белый фон на исходниках лучше "прятать" за счет оформления карточки, а не агрессивного редактирования изображений на первом этапе.
- Для первой рабочей версии лучше придерживаться почти "немого" интерфейса: без статусов, без технических подсказок и без лишнего поясняющего текста.

## Technical Notes
- Делать анимацию через `transform`, а не через свойства, которые вызывают тяжелый reflow.
- Изображения желательно предзагрузить, чтобы в момент reveal не было мигания или пустого места.
- Карточки рулетки лучше делать одинаковой ширины, чтобы упростить расчет финальной позиции.
- Нужен guard от повторного клика во время спина.
- Базовая логика должна быть отделена от визуала настолько, чтобы можно было потом свободно менять:
  - тайминги;
  - easing;
  - цвета;
  - размеры карточек;
  - плотность контента.
- Для изображений предметов базовая стратегия должна быть такой:
  - внешний контейнер карточки задает единый размер;
  - само изображение вписывается без искажения;
  - фон карточки помогает сгладить белые края или светлый исходник;
  - при необходимости можно добавить внутреннюю подложку или мягкий градиент за бутылкой.
- Маленькие товарные фото нельзя безнаказанно растягивать на всю ширину карточки: лучше ограничивать фактический размер рендера бутылки внутри контейнера.

## Suggested Folder Structure
Даже если сайт будет собран вокруг `index.html`, проект лучше держать аккуратно:

```text
/
  index.html
  assets/
    images/
  styles.css
  script.js
  PLAN.md
```

Если потом появится желание, можно объединить все в один файл, но для разработки и быстрой настройки удобнее сначала держать `HTML`, `CSS` и `JS` отдельно.

## Milestones
### Milestone 1. Skeleton
- Создать базовый `index.html`.
- Разместить каркас рулетки и CTA.
- Подключить стили и скрипт.

### Milestone 2. Static Visual
- Сделать темную базовую тему.
- Отрисовать окно рулетки и карточки предметов.
- Собрать адаптивный layout для десктопа и мобилы.
- Проверить, как выглядят узкие бутылки и более широкие банки в одном и том же карточном формате.
- Упростить интерфейс до минимального набора текста вокруг рулетки.

### Milestone 3. Spin Logic
- Добавить массив предметов.
- Реализовать выбор победителя.
- Собрать прокрутку ленты и точную остановку на предмете.

### Milestone 4. Reveal
- Сделать overlay результата.
- Показать крупный выигрыш и редкость.
- Добавить повторный запуск.

### Milestone 5. Polish
- Подкрутить длительность и ритм анимации.
- Улучшить micro-interactions кнопки и reveal.
- Проверить ощущение на мобиле.
- Оптимизировать размеры изображений.

## Risks
- Слишком разные по стилю картинки предметов разрушат цельность интерфейса.
- Слишком медленный спин убьет динамику.
- Слишком быстрый спин убьет интригу.
- Слабый reveal сделает выигрыш эмоционально пустым.
- Излишне сложный стартовый код затруднит дальнейшие эксперименты.

## Definition Of Done For MVP
Можно считать первую версию готовой, когда:

1. Страница открывается без дополнительных зависимостей.
2. Рулетка видна сразу.
3. Один клик запускает спин.
4. Лента плавно движется и замедляется.
5. Приз останавливается под маркером без визуального сбоя.
6. Победивший предмет показывается крупно.
7. Пользователь может снова запустить спин.
8. Интерфейс остается читаемым и удобным на мобильной ширине.

## Open Questions For Later
Это не мешает стартовать, но к этим вопросам мы вернемся после первой рабочей версии:

- Какие именно бренды или типы пива попадут в список?
- Нужны ли реальные вероятности выпадения или пока все одинаково вероятно?
- Будет ли один кейс или несколько тематических наборов?
- Нужны ли звуки на спин и reveal?
- Нужны ли фоновые декоративные эффекты: частицы, дымка, light streaks?
- Оставляем ли проект как "фановую демку" или готовим его как полноценный маленький продукт?

## Recommended Next Step
Следующий практический шаг после этого документа: собрать самую простую рабочую версию страницы без глубокой полировки, чтобы быстро проверить три вещи на реальном интерфейсе:

1. насколько приятно ощущается сам ритм спина;
2. достаточно ли крупно и читаемо выглядят карточки;
3. насколько эффектно воспринимается reveal победителя.
